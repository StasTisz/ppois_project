На удалённом репозитории GitHub обе ветки (origin/feature/bot-event-infra и origin/feature/bot-logic) уже указывают на один и тот же коммит 640a448. Дифф между ними абсолютно пустой. Слияние возможно чистым Fast-Forward без реверс-инжиниринга.

Подводный камень №2: data/movies.db-shm

В Git были случайно закоммичены служебные файлы SQLite (.db-shm). При локальном запуске SQLite меняет этот файл, и Git блокирует слияние: "Your local changes would be overwritten".

Решение: сбросить файл и добавить в .gitignore.
Инструкция по безопасной синхронизации для Стаса: 
# 1. Откатываем локальные изменения временного файла SQLite
git checkout -- data/movies.db-shm

# 2. Выполняем чистый Fast-Forward pull из ветки
git pull origin feature/bot-event-infra

# 3. Убираем служебные файлы БД из отслеживания Git
git rm --cached data/movies.db-shm data/movies.db-wal
echo "data/*.db-shm" >> .gitignore
echo "data/*.db-wal" >> .gitignore
git commit -m "chore: stop tracking temporary sqlite wal and shm files"
Аномалия 1: Прогрев группы пачками по 10 штук

Почему постеры уходили медленно и пачками?

1. Лимит Telegram: 20 сообщений в минуту на группу Telegram использует алгоритм Token Bucket. На старте бот отправляет залп из 10–12 фото, после чего ведро пусто и сервер возвращает HTTP 429 Too Many Requests.
2. Нереалистичный sleep 150 мс Код делал паузу всего 150 мс (~7 фото в секунду, что в 20 раз превышает допустимый лимит группы).
3. Молчаливый пропуск ошибок (Silent Drop) Блок catch (const std::exception& e) проглатывал ошибку 429. Пока бот был в бане на 25 секунд, следующие 40 фильмов просто выбрасывались. Когда Telegram снимал бан — уходило ещё 10 фильмов.
Аномалия 2: Задержка 2 сек и отсутствие постеров в чате

Почему постеров не было, а ответ шёл 1–2 сек?

КРИТИЧЕСКИЙ БАГ: INSERT OR REPLACE в DatabaseManager При каждом старте метод seedMoviesFromJson выполнял: INSERT OR REPLACE INTO movies (id, title, ..., trailer_url) В SQLite INSERT OR REPLACE удаляет строку и вставляет новую. Колонка poster_file_id при этом затирается в NULL для ВСЕХ 60 фильмов при каждом перезапуске!
Почему ответ занимал 1.5–2 секунды: Так как кэш в базе обнулялся, бот всегда отправлял веб-ссылку TMDB (https://image.tmdb.org/...). Сервер Telegram сам шёл в интернет, скачивал картинку и пережимал её. Этот сетевой цикл занимает 1200–2000 мс (вместо 50 мс по file_id).
Почему постер пропадал и приходил только текст: В sendPhotoWithKeyboard было задано maxRetries = 0. При любой сетевой задержке отправка фото возвращала false, и форматер переключался в текстовый fallback.

Сравнение путей доставки постера:

Текущий путь (по внешнему URL TMDB / сброс базы): 1800 мс
Клиент → Бот → Telegram API → Загрузка по внешнему URL из TMDB → Обработка CDN → Пользователь
Целевой путь (по сохранённому Telegram file_id): 45 мс (в 40 раз быстрее!)
Клиент → Бот → Мгновенная отдача готового фото с CDN Telegram по внутреннему идентификатору

Паттерн Proxy / Decorator

Кэширующий репозиторий фильмов

Исключение постоянных медленных чтений каталога фильмов из файла базы данных SQLite.

Создать класс CachedMovieRepository : public IMovieRepository, который хранит каталог в оперативной памяти и прозрачно кэширует запросы. Образцовая демонстрация полиморфизма.
Паттерн Observer (Наблюдатель)

Шина событий для сбора метрик

Сделать шину EventBus. При оценке фильма публикуется событие MovieRatedEvent. MetricsCollector подписан на шину, обеспечивая слабую связность (Low Coupling).

MovieCardBuilder для карточек
